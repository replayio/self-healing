# Factory dashboard

## Opening and authentication

Call `POST /api/v1/dashboard-sessions` with the existing Self Healing bearer key after connecting the project. No body is required. The response contains `url`, `expires_at`, and `session_ttl_seconds` (604800). A factory should display the returned URL as **Open dashboard** when requested, rather than saving a permanent link.

The launch link can be opened multiple times during its seven-day lifetime. Its ticket is in a URL fragment, so it is not sent in HTTP requests or referrers. The dashboard keeps it available during redemption and removes it from browser history only after a successful POST to `/api/v1/dashboard/redeem`. That same-origin exchange creates a new browser token and sets a Secure, HttpOnly, SameSite=None, Partitioned, host-only cookie. It does not consume or extend the launch link: an agent opening it does not invalidate it for the user.

Each browser session has an absolute, server-checked seven-day expiry; refreshing does not extend it. A redemption can be retried while the link is valid. After the link expires, existing browser sessions continue to work, but new openings need a fresh link. Logout deletes only the current browser token; other sessions and a still-valid launch link remain usable. Opening a different project's link switches the current browser's dashboard session to that project.

Only dashboard GET routes accept this cookie; launch creation and existing factory APIs still require the bearer key. No provider keys or account API keys are sent to the browser. The launch ticket and browser token are capabilities and should not be published. There is no new signup or user login flow.

Migration `005_dashboard_sessions.sql` stores token hashes, account scope, kind and expiry. Expired rows are pruned when creating launch links. Deployment applies the migration through the existing pipeline. No new secrets are required. Overview reads require QA’s project aggregate APIs (QA PR #5088). `SELF_HEALING_URL` must be the HTTPS origin for that environment. A preview must use isolated credentials/database and its own origin. Local UI development can use fixtures; a full cookie exchange needs HTTPS.

## Data ownership and definitions

The dashboard reads existing QA APIs using the connection's dedicated QA token. The Sessions viewer reads Subtext through Self Healing using the account’s retained key, after verifying the requested session belongs to the connected QA project. It does not persist session/report contents. Bug reports are read through Self Healing using the same dashboard session; users do not need QA project access. The server checks each bug’s project against the authenticated connection before returning a whitelist of report fields.

- The overview card shows all-time bug counts for the connected QA project, with open bugs prominent and fixed, wontfix, and invalid counts below. Open includes `open` and `reopened`; the other three counts match their exact QA statuses. `pr-closed` and unconfirmed (`judge-rejected`) reports are excluded from these four counts. The API retains its combined closed, rolling-24-hour new-open, and session totals for compatibility.
- A second overview card shows the rolling last-24-hour session success rate: `(total sessions − sessions with serious errors) / total sessions`, with both counts below. The window uses first-received timestamps, includes unreviewed sessions, and shares the graph's serious-issue definition. Zero sessions displays no rate. “Success” means no detected serious error, not proof that an unreviewed session was problem-free. The two cards sit side by side on desktop and stack on mobile.
- The graph covers the last 30 UTC dates, including today, bucketed by QA's `first_received_at`, the same session-start basis used by QA charts. QA computes daily aggregates over that date range through the request's captured end time. All sessions form the denominator, including unreviewed ones; review coverage is shown per day.
- A session has a detected bug when a QA reviewer context associates it with at least one bug other than `judge-rejected` or `invalid`. This includes fixed bugs: the chart records detection, not current backlog. QA's current reviewer-context semantics choose the latest successful review; this is not an immutable historical snapshot.
- A serious issue is a non-deleted friction-and-recovery observation with `attributes.impact === "blocked"`, using that reviewer's existing vocabulary. `delayed` and `minor` do not qualify. Repeated observations and associations across reviewers count a session only once.
- Each column's total height is its session count, split into “No friction” and “Friction.” Friction uses the serious-issue definition above (blocked user progress), regardless of bug associations. Hovering or focusing a column shows a compact tooltip with its date, session total, and aligned counts and percentages for both categories. The tooltip disappears on mouse leave, blur, or Escape; accessible column labels retain the same data. “No friction” means no detected friction; unreviewed sessions may still contain issues.
- Bugs has separate Open bugs and Closed bugs sections. The closed section includes `fixed`, `wontfix`, `invalid`, and `pr-closed`, excludes unconfirmed reports, and filters the complete QA list before paginating. The open section uses QA's paginated `status=open` filter, which includes reopened bugs. Sorting is highest severity first across pages (critical, high, medium, low), then newest first. The table includes QA bug kinds and linked fix pull requests. Bug links (including those in daily reports) open `/dashboard?tab=bugs&bug=<id>`. The detail page reads `GET /api/v1/dashboard/bug?bug_id=<id>` and shows the description, behavior, reproduction, analysis, notes, resolution and fix PRs. Root cause, walkthrough and causal-chain evidence appears in expandable cards with tool labels, parameter previews, full parameters and results, matching QA’s evidence disclosures. All pages are accessible using Previous/Next.
- Reports reads the connection's daily summarizer. It shows QA's overview, new/duplicate bug lists sorted highest severity first and expandable User trends/Friction findings, with bug evidence links. Reviewer identity, configuration and review panels are not exposed. Previous/Next follows QA's older/newer report dates; the date picker can request any completed day, and Latest restores the latest available report. Missing, queued and failed reports remain explicit.

The dashboard has horizontal Overview, Reports, Bugs and Sessions tabs with no sidebar, including at narrow iframe widths. The page permits iframe embedding. A Secure, HttpOnly, SameSite=None, Partitioned cookie supports cross-site frames and isolates each embedding site’s browser session. Embed the returned launch URL directly; no proxy or parent-site access to credentials is needed. A sandboxed iframe must allow scripts and same-origin access. The cookie name is versioned to avoid collisions with old unpartitioned cookies; existing users can open a fresh dashboard link after this update.

Sessions lists every captured session by first-received UTC day, with 50-row pagination. Opening a session reads Subtext’s full machine timeline through `review-open` and `review-zoom`. Interaction screenshots use image-only `review-snapshot`, queued one at a time as their rows become visible to avoid a burst of concurrent review clients. Canceled rows are skipped. The component tree and raw timeline are not displayed. Each request closes its Subtext review client. This works without a QA reproduction journey and does not enqueue QA analysis. Failures identify the Subtext operation, HTTP status (when available), timeout or response-size limit, rather than claiming all failures mean the session is still processing; missing screenshots are explicit. Every review receives the connected QA project’s sightmap, including nested component selectors and memory. A missing/not-yet-generated sightmap permits raw labels; other sightmap read failures remain explicit. Subtext’s caret datamarkers are displayed as spaces in interaction labels. No new secrets or migrations are required.

Read-only dashboard routes: `GET /api/v1/dashboard/sessions?day=YYYY-MM-DD&page=0`, `/session?session_id=...`, and `/session-snapshot?session_id=...&timestamp=<milliseconds>`. Session IDs are resolved within the authenticated connection before any Subtext read; clients cannot supply provider URLs or credentials.

Overview makes three concurrent calls to QA’s general-purpose `/api/project-aggregates/bugs` and `/api/project-aggregates/sessions` endpoints: all-time/current-status bug counts with recent discovery counts, daily session aggregates, and exact rolling-24-hour session totals. All use the authenticated connection's project ID and dedicated QA token. QA handles deduplication, latest successful reviewer selection, deleted observations, and bug/observation overlap in SQL; Self Healing only maps aggregate fields and sums status counts. It downloads no individual bug, session, or review records for Overview.

All three requests share one captured end time and use QA's half-open `[from, to)` intervals: the lower bound is included, and records exactly at or after the captured end time are excluded. At exactly UTC midnight, today's chart date remains visible with zero counts even though it has no intersecting QA bucket. All other daily buckets must be present and ordered. The response shape and frontend are unchanged.

Deploy QA PR #5088 before this consumer update. No Self Healing migration or new credentials are needed. Upstream errors (including an unavailable aggregate endpoint), malformed data, mismatched project IDs, or incomplete daily series fail visibly rather than returning partial counts or falling back to expensive pagination. Each aggregate response has one database-statement snapshot; concurrent upstream changes can still differ across the three responses. The closed-bug list continues to collect paginated QA records on demand.
